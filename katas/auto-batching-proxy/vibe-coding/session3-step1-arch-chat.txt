  # Architecture

  ## Main objects

  - `Batcher`: the main logic
  - `ActiveVector`: a wrapper over `Vec`, to limit its functionality and to
   notify listeners
  - `Timer`: to notify when waiting is over

  ## Main logic

  - The service handler accepts a query
  - The handler passes the query to `Batcher`, which returns a 
  `tokio::sync::oneshot` promise
  - The handler awaits on the promise and returns the result

  The result from `Batcher` includes http status code to report potential 
  errors.

  `Batcher` unpacks individual text fragments from the input and stores 
  them in `ActiveVector`, together with the promise and the current 
  timestamp.

  Eventually, `Batcher` is notified with resolved embeddings. It should 
  walk over the resolved batch, merge items of the same promise and resolve
   the promise.

  ## Background logic

  `Batcher` waits for "time to embed a batch" events in an infinite loop. 
  On an event:

  - Check if the event valid: The timer is allowed to trigger earlier, or 
  its notification can be for an old batch
  - Get a new batch from `ActiveVec`. If it is empty, continue waiting for 
  new events
  - Otherwise, call the embedding service and pass the result to the main 
  logic

  ## ActiveVec

  `ActiveVec` wraps a Vec of records (text fragment, promise, timestamp, 
  whatever) which are waiting to be batched.

  Method `extend` adds several items of one promise to the vector.

  Method `slice` extract a batch from the vector, up to the configured 
  maximal size. Items of one promise should not be broken, consider 
  "maximal size" as a recommendation in this case.

  `ActiveVec` should trigger callbacks:

  - To timer: There is a new first element. As a parameter, pass the 
  injection timestamp
  - To the background logic: The size of the vector is more or equal than 
  the maximal size

  ## Timer

  Timer is reset each time a new `set` is called.

  ## Special considerations

  The service should eventually stop on SIGSTOP.

  In the names for "Max Wait Time" and "Max Batch Size" include the word 
  "soft", to adjust user expectations.

  Return "503 Service Unavailable" if there are too much (let's say 10x of 
  the configured vector max size) unprocessed items, including those which 
  are in process by the upstream embedding service.

● Task Specification for Middle Developer

  Overview

  Implement an auto-batching proxy service in Rust that aggregates
  individual text embedding requests into efficient batches before
  forwarding to a HuggingFace text-embeddings-inference service.

  Core Components to Implement

  1. HTTP Server (src/server.rs)

  - Framework: Use axum web framework
  - Endpoints:
    - POST /embed - Main endpoint accepting {"inputs": ["text1", "text2"]}
    - GET /health - Health check endpoint
  - Error Handling: Return appropriate HTTP status codes (200, 503, 500)

  2. Batcher (src/batcher.rs)

  - Core Logic: Accept requests, return
  tokio::sync::oneshot::Receiver<Result<Vec<Vec<f32>>, BatchError>>
  - Integration: Manage ActiveVector and Timer instances
  - Background Task: Infinite loop processing batch events
  - Backpressure: Return 503 when queue exceeds 10x max batch size

  3. ActiveVector (src/active_vector.rs)

  - Data Structure: Vec<BatchItem> where BatchItem contains text, oneshot
  sender, timestamp, request_id
  - Methods:
    - extend() - Add items from single request
    - slice() - Extract batch respecting request boundaries
  - Callbacks: Notify timer and batcher of size/timing triggers

  4. Timer (src/timer.rs)

  - Functionality: Reset on each set() call, trigger after max wait time
  - Integration: Use tokio::time::sleep and channels for notifications

  5. Configuration (src/config.rs)

  - Parameters:
    - SOFT_MAX_WAIT_TIME_MS (default: 100ms)
    - SOFT_MAX_BATCH_SIZE (default: 32)
    - UPSTREAM_URL (HuggingFace service)
  - Loading: Environment variables with defaults

  6. HTTP Client (src/client.rs)

  - Library: Use reqwest for upstream calls
  - Endpoint: POST to /embed with JSON payload
  - Error Handling: Network timeouts, parsing errors

  Technical Requirements

  - Async Runtime: tokio with #[tokio::main]
  - Serialization: serde with serde_json
  - Logging: tracing with structured logging
  - Signal Handling: Graceful shutdown on SIGTERM
  - Testing: Unit tests for each component, integration test for end-to-end
   flow

  Success Criteria

  1. ✅ Service batches requests efficiently within time/size constraints
  2. ✅ Individual requests receive correct embeddings in proper order
  3. ✅ 503 responses when overwhelmed
  4. ✅ Graceful shutdown preserves in-flight requests
  5. ✅ Docker compose setup with benchmark results

  Key Implementation Notes

  - Keep request items together in batches (don't split single requests)
  - Use "soft" limits - prioritize not breaking requests over exact size
  limits
  - Handle upstream service failures gracefully
  - Maintain request-response correlation through the batching process
